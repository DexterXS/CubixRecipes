# CubixWorld Item Intelligence — Roadmap

Этот документ фиксирует порядок следующих этапов разработки базы предметов CubixRecipes.

## Текущее состояние

Уже есть:
- отдельная `Postgres-ItemIntelligence` в Railway;
- test-интерфейс «База предметов»;
- lazy loading: лёгкий индекс + точечная загрузка паспорта/истории/метрик/evidence;
- серверный поиск по всей базе;
- импорт серверных цен;
- специальная обработка `999999` как запрета продажи;
- история изменения цены предмета;
- отдельные источники/evidence и редактируемый паспорт.

## Stage A — автоматическое заполнение базового паспорта

Цель: заполнить всё, что уже известно из внутренних/локальных источников, без тяжёлого графового анализа.

Автоматически собирать и заполнять:
- `registry_key`, `meta`, NBT;
- `mod_id` и название мода;
- RU/EN название;
- OreDictionary;
- иконку и путь к текстуре;
- Legacy ID;
- stackability / max stack;
- durability, если доступно;
- item type / category;
- server context;
- технические поля;
- уже импортированную экономику;
- `source_count`, `source_summary`, `last_verified_at`, `confidence`.

Для каждого факта обязательно сохранять provenance: источник, confidence, дата проверки и evidence.

Нужен отдельный background/import job с прогрессом, например:
`Basic enrichment: 12400 / 29145`.

## Stage B — enrichment по модам

Цель: по одному моду дополнять содержательную часть паспорта.

Собирать:
- описание;
- назначение;
- tier;
- редкость;
- особенности;
- способы получения;
- ограничения;
- серверные конфиги/overrides;
- официальные wiki/docs/GitHub/CurseForge/другие внешние источники.

Важно: серверная конфигурация CubixWorld имеет приоритет над общими данными о стандартном моде.

## Stage C — Usage / Recipe Index

Цель: автоматически определить реальную важность предмета в рецептах основного сервера.

Для каждого предмета считать:
- `recipe_input_count` — число уникальных активных рецептов, где предмет используется как input;
- `recipe_output_count` — число рецептов, где предмет получается;
- `usage_quantity_total` — суммарное количество предмета в рецептах;
- `crafting_recipe_count`;
- `machine_recipe_count`;
- `downstream_item_count` — сколько разных предметов зависят от него;
- список `used_in_recipes`;
- список `produced_by_recipes`;
- `usage_score`;
- `usage_rank`.

Основная метрика частоты использования — количество уникальных активных рецептов, а не только суммарное количество предметов.

Источник рецептов должен быть основной CubixWorld / production, а не test.

## Stage D — расчёт ценности и баланса

После появления базовых данных и Recipe Index рассчитывать:
- Market Value;
- Craft Value;
- Progression Value;
- Utility Value;
- Rarity Value;
- Acquisition Cost;
- Final Value Score;
- Priceless rank для предметов без нормальной цены;
- аномалии/imbalance.

В расчёты учитывать:
- серверную цену;
- запрет продажи;
- частоту использования в рецептах;
- сложность получения;
- progression/tier;
- rarity;
- зависимости по крафтам;
- серверные конфиги и ограничения.

`999999` никогда не использовать как реальную цену: это серверный маркер «продажа запрещена» и такие записи должны исключаться из market price calculations.

## Общие принципы

- Server truth first.
- Price != value.
- Unknown остаётся unknown, не выдумывать значения.
- Хранить несколько conflicting claims, а не затирать их.
- Каждое поле должно иметь provenance/evidence.
- Версия сервера/мода/сборки должна учитываться в контексте данных.
- UI должен оставаться lazy: не отдавать клиенту всю тяжёлую базу.
- Цель автоматизации: не более ~20% ручной корректировки.

## Ближайший следующий шаг

Начать с **Stage A: Basic Enrichment**. После его стабилизации перейти к **Stage C: Usage / Recipe Index**, потому что это даст один из самых объективных сигналов важности предмета для дальнейшей оценки ценности.
